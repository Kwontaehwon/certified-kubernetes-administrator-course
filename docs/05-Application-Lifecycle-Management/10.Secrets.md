## Web-Mysql Application

 ![web](../../images/web.PNG)
 
- 한 가지 방법은 앱 속성/환경 변수를 configmap으로 이동하는 것입니다. 그러나 configmap은 데이터를 일반 텍스트 형식으로 저장합니다. 비밀번호를 저장하기에는 적절한 장소가 아닙니다.
  ```
  apiVersion: v1
  kind: ConfigMap
  metadata:
   name: app-config
  data:
    DB_Host: mysql
    DB_User: root
    DB_Password: paswrd
  ```
  ![web1](../../images/web1.PNG)
  
- Secrets는 민감한 정보를 저장하는 데 사용됩니다. configmap과 유사하지만 암호화된 형식이나 해시된 형식으로 저장됩니다.

#### Secrets에는 2단계가 포함됩니다.
- 첫 번째, secret을 생성합니다.
- 두 번째, secret을 pod에 주입합니다.
  
  ![sec](../../images/sec.PNG)
  
#### Secret을 생성하는 방법은 2가지가 있습니다.
- 명령형 방법
  ```
  $ kubectl create secret generic app-secret --from-literal=DB_Host=mysql --from-literal=DB_User=root --from-literal=DB_Password=paswrd
  $ kubectl create secret generic app-secret --from-file=app_secret.properties
  ```
  ![csi](../../images/csi.PNG)
  
- 선언형 방법
  ```
  비밀번호의 해시 값을 생성하고 이를 secret-data.yaml 정의 값으로 DB_Password 변수의 값으로 전달합니다.
  $ echo -n "mysql" | base64
  $ echo -n "root" | base64
  $ echo -n "paswrd"| base64
  ```
  
  secret 정의 파일을 생성하고 `kubectl create`를 실행하여 배포합니다.
  ```
  apiVersion: v1
  kind: Secret
  metadata:
   name: app-secret
  data:
    DB_Host: bX1zcWw=
    DB_User: cm9vdA==
    DB_Password: cGFzd3Jk
  ```
  ```
  $ kubectl create -f secret-data.yaml
  ```

  ![csd](../../images/csd.PNG)

## Secrets 보기
- secrets를 보려면 (value는 안보여주고 Byte 수만)
  ```
  $ kubectl get secrets
  ```
- secret을 설명하려면
  ```
  $ kubectl describe secret
  ```
- secret의 값을 보려면
  ```
  $ kubectl get secret app-secret -o yaml
  ```
  
  ![secv](../../images/secv.PNG)
  
## Secrets 디코딩
- secrets를 디코딩하려면
  ```
  $ echo -n "bX1zcWw=" | base64 --decode
  $ echo -n "cm9vdA==" | base64 --decode
  $ echo -n "cGFzd3Jk" | base64 --decode
  ```
  ![secd](../../images/secd.PNG)
  
## Pod와 함께 secret 구성하기
- secret을 pod에 주입하려면 새로운 속성 **`envFrom`**을 추가하고 **`secretRef`** 이름을 지정한 후 pod 정의를 생성합니다.
  
  ```
  apiVersion: v1
  kind: Secret
  metadata:
   name: app-secret
  data:
    DB_Host: bX1zcWw=
    DB_User: cm9vdA==
    DB_Password: cGFzd3Jk
  ```
  ```
   apiVersion: v1
   kind: Pod
   metadata:
     name: simple-webapp-color
   spec:
    containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      ports:
      - containerPort: 8080
      envFrom:
      - secretRef:
          name: app-secret
   ```
  ```
  $ kubectl create -f pod-definition.yaml
  ```
  ![secp](../../images/secp.PNG)
  
#### Pods에 secrets를 주입하는 다른 방법이 있습니다.
- **`Single ENV variable`**로 주입할 수 있습니다.
- **`Volume`**에 파일로 전체 secret을 주입할 수 있습니다.

  ![seco](../../images/seco.PNG)

> [!Warning] `Secret` 보안
> 단지 base64로 인코딩 된 것 이기 때문에 Github에 Secret Object를 Push 하지 말아라.

#### 추가 노트: [Secrets에 대한 노트](https://kodekloud.com/topic/a-note-on-secrets/)

secrets는 데이터를 base64 형식으로 인코딩합니다. base64로 인코딩된 secret을 가진 사람은 쉽게 디코딩할 수 있습니다. **따라서 secrets는 그리 안전하다고 볼 수 없습니다.**

Secrets의 안전성 개념은 Kubernetes에서 다소 혼란스러울 수 있습니다. [kubernetes 문서](https://kubernetes.io/docs/concepts/configuration/secret) 페이지와 많은 블로그에서는 secrets를 민감한 데이터를 저장하는 "더 안전한 옵션"으로 언급합니다. 이는 일반 텍스트로 저장하는 것보다 안전하며 비밀번호 및 기타 민감한 데이터를 우연히 노출할 위험을 줄입니다. 제 생각에는 안전한 것은 secret 자체가 아니라 그 주변의 관행입니다.

Secrets는 암호화되지 않으므로 그 의미에서 더 안전하지 않습니다. 그러나 secrets를 사용하는 몇 가지 모범 사례는 이를 더 안전하게 만듭니다. 예를 들어:

- secret 객체 정의 파일을 소스 코드 리포지토리에 체크인하지 않기.
- **[Encryption at Rest 활성화](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)를 통해 secrets가 ETCD에 암호화되어 저장되도록 하기.**

또한 kubernetes가 secrets를 처리하는 방식도 있습니다. 예를 들어:

- secret은 해당 노드의 pod가 필요할 때만 노드로 전송됩니다.
- Kubelet은 secret을 tmpfs에 저장하여 secret이 디스크 저장소에 기록되지 않도록 합니다.
- secret에 의존하는 Pod가 삭제되면 kubelet은 secret 데이터의 로컬 복사본도 삭제합니다.

secrets 사용에 대한 [보호 조치](https://kubernetes.io/docs/concepts/configuration/secret/#protections) 및 [위험](https://kubernetes.io/docs/concepts/configuration/secret/#risks)에 대해 [여기](https://kubernetes.io/docs/concepts/configuration/secret/#risks)에서 읽어보세요.

그렇다고 하더라도 Kubernetes에서 비밀번호와 같은 민감한 데이터를 처리하는 더 나은 방법이 있습니다. 예를 들어 Helm Secrets, [HashiCorp Vault](https://www.vaultproject.io/)와 같은 도구를 사용하는 것입니다. 앞으로 이에 대한 강의를 할 수 있기를 바랍니다.
